# 工程化工具链

本页是 Aura 仓库**工具链层面的地图**：每一层用什么工具、守护什么、在哪一道门禁里生效。
编码规范与性能基线的条款本身见 [开发规范与性能指标](/guide/standards)，两页互补不重复。

> 所有版本号取自 `package.json` / `.nvmrc`；「实测」数据标注了测量命令。

## 一、分层总览

| 层           | 工具                             | 版本                                                          | 守护什么                                                                       |
| ------------ | -------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 工作区       | pnpm workspace                   | **7.33.7**（`packageManager` 锁定，CI 同版本）                | 8 个包的单仓管理与跨包解析（`workspace:*`）                                    |
| 运行时       | Node.js                          | `.nvmrc` = **24**；`engines` = `^20.19 \|\| ^22.13 \|\| >=24` | 构建与 CI 的运行时基线                                                         |
| 类型         | TypeScript                       | **^6.0.3**，`strict: true`                                    | 类型正确性、跨包 `paths` 解析、导出协议                                        |
| 检查         | ESLint                           | **^10**（flat config）                                        | 未使用变量、Hooks 规则、禁止 `any`                                             |
| 格式         | Prettier                         | **^3.9.6**（printWidth 80）                                   | 代码风格（**当前未入门禁**，见「五」）                                         |
| 测试         | Vitest + jsdom + Testing Library | **^1.6** / `@testing-library/react` ^16                       | 行为正确性、覆盖率阈值                                                         |

| 提交规范     | husky + lint-staged + commitlint | **^9 / ^17 / ^21**                                            | 暂存代码自动修复、提交信息符合 Conventional Commits                            |

### 包形态（8 个）

| 形态      | 包                                                       | 构建方式                          |
| --------- | -------------------------------------------------------- | --------------------------------- |
| 库包（6） | `shared` / `request` / `icons` / `ui` / `business` / `x` | `father build` → `esm/` + `.d.ts` |
| 工具包    | `cli`                                                    | `tsc`（MCP Server，bin: `aura`）  |
| 资产包    | `skill`                                                  | 无构建，纯 Markdown 提示词资产    |

`@aura/x` 在 `father build` 之后额外跑 `scripts/build-styles.mjs`：把 `src/**/*.less`
合并为 `esm/style.css`，并从 `esm/**/*.js` 剥离 `.less` 副作用导入——
消费方构建器（如 Next.js）没有 less 管线，留着会导致安装即构建失败。

### 关键约定：包清单不写死

`postbuild-dts.mjs` 与 `smoke.mjs` 的**包清单是按 `packages/*/package.json` 的
`scripts.build` 是否含 `father build` 自动派生**的，并带「推导结果为空则报错退出」的兜底。

这条约定来自一次真实事故：`@aura/x` 加入 workspace 时，三处手写清单（含根
`package.json` 的 `size-limit`）都没同步，导致它的声明文件长期残留样式导入、
9 项产物校验全部空转。**新增包后请确认这三处都已自动覆盖。**

## 二、门禁矩阵

三道关卡，覆盖面逐级增强：

| 检查                                                       | pre-commit |       `pnpm verify`       | CI（`ci.yml`） |
| ---------------------------------------------------------- | :--------: | :-----------------------: | :------------: |
| `eslint --fix`（仅暂存的 `*.{ts,tsx}`）                    |     ✅     |             -             |       -        |
| `prettier --write`（仅暂存的 `*.{json,less,md,yml,yaml}`） |     ✅     |             -             |       -        |
| `commitlint`（提交信息）                                   |     ✅     |             -             |       -        |
| `pnpm lint`                                                |     -      |            ✅             |       ✅       |
| `pnpm typecheck`                                           |     -      |            ✅             |       ✅       |
| 单元测试                                                   |     -      |            ✅             |       ✅       |
| **覆盖率阈值**                                             |     -      |            ✅             |       ✅       |
| `pnpm build:lib`                                           |     -      |            ✅             |       ✅       |
| `postbuild-dts` 声明清理                                   |     -      | ✅（链在 `build:lib` 内） |       ✅       |
| `pnpm size` 体积预算                                       |     -      |            ✅             |       ✅       |
| `pnpm smoke` 产物冒烟                                      |     -      |            ✅             |       ✅       |
| `pnpm format:check`（收敛进度探针，**未入门禁**）          |     -      |            ❌             |       ❌       |

一键执行：

```bash
pnpm verify       # 完整门禁：lint → typecheck → test:coverage → build:lib → size → smoke
pnpm verify:fast  # 跳过覆盖率插桩，用于紧凑的内循环
```

> 本地 `verify` 与 CI **跑的是同一条链路**（都含覆盖率阈值）。
> 需要更快的反馈时用 `verify:fast`——它只是省掉覆盖率插桩，
> **推送前仍应跑一次完整的 `pnpm verify`**。

CI 的两个工作流：

- `ci.yml` — push / PR 到 `master` 触发；用 `concurrency.cancel-in-progress`
  取消同分支的旧运行；安装时统一带 `--ignore-scripts`（跳过 root 的
  `prepare: dumi setup`，该步骤在 CI 中会拖慢乃至卡住）。
- `deploy.yml` — push 到 `master` 或手动触发；`dumi build` 后经 OIDC 部署到 GitHub Pages。

## 三、任务编排

**结论：仓库没有引入任何专用任务编排器**——没有 Turbo / Nx / Lage / Rush / Wireit /
concurrently / npm-run-all 的配置与依赖。编排由各层原生机制分担：

| 层次       | 谁在编排            | 机制                                                                                                                                                               |
| ---------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **包级**   | pnpm                | `-r` 递归 + **按工作区依赖图拓扑排序**（`--no-sort` 可关闭）；`--workspace-concurrency` 默认 **4** 并发；`--filter <包名>` 做单包操作；无 `build` 脚本的包自动跳过 |
| **步骤级** | npm scripts         | `&&` 线性链：`verify` 6 步、`build:lib` 2 步、`prepare` 2 步                                                                                                       |
| **测试级** | Vitest              | 按文件并行（线程池）；`--coverage` 时额外断言覆盖率阈值                                                                                                            |
| **钩子级** | husky + lint-staged | 只对**暂存**文件跑 `eslint --fix`；commitlint 校验提交信息                                                                                                         |
| **CI 级**  | GitHub Actions      | `ci.yml` 单 job 内 6 个串行 step；`deploy.yml` 用 `needs: build` 建立 job 依赖；`concurrency` 组控制运行并发；`cache: 'pnpm'` 复用 store                           |

### 包依赖图与拓扑顺序

跨包依赖全部用 `workspace:*` 声明，这张图就是 pnpm 的排序依据：

```text
icons ──┐
        ├──→ ui ──┐
shared ─┤         ├──→ business
        ├──→ request
        └──→ x
```

实测顺序（`pnpm -r --workspace-concurrency=1 exec`，依赖包先于依赖方）：

```text
cli  icons  shared  skill     ← 叶子包，无 workspace 依赖
request                       ← 依赖 shared
ui                            ← 依赖 icons + shared
x                             ← 依赖 shared
business                      ← 依赖 shared + ui，最深，最后执行
```

> 注意：`@aura/skill` 没有 `build` 脚本，`pnpm -r build` 会自动跳过它——
> 这也是为什么它作为「纯 Markdown 资产包」不需要排除配置。

### 什么场景才值得上编排器

编排器（Turbo / Nx / Lage）买的是**「消除重复劳动」**。所以只有当
**重复劳动的量 × 触发频次**足够大、而且这份劳动**可缓存**时才回本。

**三个必要条件，缺一不可：**

| 条件                       | 量化信号                                                        | 为什么是前提                                                                                     |
| -------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **有可缓存的昂贵产物**     | 单次全量构建 > 1~2 分钟，且产物可哈希（bundle / 生成物 / 类型） | 缓存是编排器的主要价值来源。纯转译（tsc / babel + bundless）是几十秒级的轻活，缓存省不出多少     |
| **存在真实的跨包产物依赖** | A 的构建需要**读 B 的产物**，而不只是 B 的源码                  | 只有产物依赖才让拓扑排序与「增量跳过」有意义。只共享源码时，构建顺序与正确性无关，缓存命中率也低 |
| **触发频次足够高**         | 本地 + CI 每天几十次全量验证，或多人并行 PR                     | 摊销配置、调试与团队学习成本                                                                     |

**组件库特有的加分场景**（命中两条以上就值得认真评估）：

1. **一套源码出多份产物**——ESM / CJS / UMD / SSR 构建 + 多框架适配（React / Vue / Angular）：
   包数与构建轮次成倍增长，这是缓存收益最大的形态；
2. **monorepo 里混着「重活」**——SSR / Web Components 打包、图标字体或 SVG 生成、
   Storybook、E2E、视觉回归、API 文档生成；
3. **包数量上双**——人工维护任务顺序与依赖关系开始出错，编排器的图能力才真正值钱；
4. **CI 分钟数受限或排队严重**——`affected-only` 能显著削峰；
5. **发布频率高**——需要按改动自动判定「这次该发哪些包」。

**「不值得」的信号**（多数中小型组件库都在这一档）：

- 包数 < 10，全量构建 + 测试 < 1 分钟；
- 包之间**只共享源码、不共享产物**（bundless 转译 + 各自产出 `.d.ts`）；
- 没有重活：只有转译与单元测试；
- 单人维护、一天几次 push；
- 编排器的配置与调试面 > 它省下的时间。

**上编排器之前，先做这五件更便宜的事**（按性价比排序）：

1. **量化瓶颈**：给 `verify` 的各步骤分别计时。组件库的耗时大头**通常是测试与文档站构建，
   而不是包构建**——若瓶颈不在构建，Turbo 帮不上忙；
2. **选择性执行**：用 pnpm 原生的 `--filter '...[origin/master]'` 只跑「改动包 + 依赖它的包」，
   零额外依赖；
3. **用例级增量**：Vitest 的 `--changed` 与分片（`--shard`）；
4. **CI 路径过滤**：给 E2E / 视觉回归这类慢任务加 `paths:` 触发条件，无关改动不跑；
5. **缓存安装**：pnpm store + CI cache（本仓已有 `cache: 'pnpm'`）。

**别混淆两类编排**：Turbo / Nx 解决的是**构建编排**（任务图 + 缓存）；而组件库更常缺的
是**发布编排**——版本提升、CHANGELOG、tag、多包联动发版，那是 **changesets** 的领域
（本仓缺的正是这个，见「五、已知缺口」）。把两件事分开看，可避免
「上了 Turbo 就能自动发版」这类误判。

### 为什么这个规模不加编排器

本仓目前的量级是 8 个包（7 个有 `build`）、870 个用例、`verify` 全链路约 40s。
对照上一节的三个必要条件，**前两条都不成立、第三条也不强**：

- **产物不昂贵**：father 是 bundless 转译，6 个库包全量构建是几十秒级的轻活；
- **没有跨包产物依赖**：各包 `tsconfig.json` 的 `paths` 全部指向
  `../<包名>/src/index.ts`（**源码**），而 father bundless 又把裸包名保持为外部导入、
  不打包跨包代码——也就是说构建 `business` 时**根本不会去读 `ui/esm`**。
  所以拓扑顺序只影响观感，不影响正确性（`--no-sort` 也能构建成功），
  缓存的命中空间也因此很小；
- **触发频次低**：单人维护、一天几次 push。

反过来，仓库**已经具备引入编排器的前提**：跨包依赖用 `workspace:*` 声明得很干净
（见上方依赖图），未来真要上 Turbo，可以直接消费这份图，无需改造。

**选型**：Turbo 配置最少、直接读 pnpm workspace 图、且支持远程缓存；
或升级 pnpm 后使用其内建的 `tasks` + `dependsOn` 声明式任务图
（pnpm 10+ 才有，本仓的 pnpm 7.33.7 不支持）。

### 换编排器时别丢掉的两处设计

1. **`build:lib` 里的串行栅栏**：`pnpm -r build && node scripts/postbuild-dts.mjs`——
   声明清理必须在**全部构建完成之后**统一执行，不能按包并行，否则会与 father 的
   产物流水线竞争。同理 `@aura/x` 的 `build-styles.mjs` 必须跟在它自己的 `father build` 之后。
2. **包清单的自动派生**：`postbuild-dts.mjs` / `smoke.mjs` 按 `scripts.build` 是否含
   `father build` 推导要处理的包，而不是写字面量数组。换成 Turbo 的 `pipeline`
   （按任务名声明、天然覆盖所有包）时，这份派生思路仍然值得保留。

## 五、已知缺口

按优先级排列。**P0（「看起来有、实际没有」的假门禁）目前为空**——
两处已处理：`format:check` 的角色与退出判据已明确 + 提交期强制格式；
本地 `verify` 已与 CI 对齐（含覆盖率阈值）。以下为 P1 / P2。

| 优先级 | 缺口                                          | 证据                                                                                                                                                                                                                       | 建议                                                                                                                  |
| ------ | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| P1     | 无版本与发布自动化                            | 无 `.changeset/`；8 个包版本统一停在 `0.0.1` 且全部 `private: true`                                                                                                                                                        | 引入 changesets 管理版本与 CHANGELOG（正式发布前必须）                                                                |
| P2     | 无构建缓存、无「只跑受影响的包」              | `pnpm -r build` 每次都全量重建 7 个包；只改了单包时也只能手动 `--filter @aura/x build`（见「三、任务编排」）                                                                                                               | 当前 40s 的全量链路不值得上编排器；规模变大后再评估 Turbo                                                             |
| P2     | 无 E2E / 视觉回归                             | 无 Playwright / Cypress 配置                                                                                                                                                                                               | 文档站关键路径可考虑 Playwright 冒烟                                                                                  |
| P2     | 无 a11y 静态检查                              | 未安装 `eslint-plugin-jsx-a11y`（直接与传递依赖均无）                                                                                                                                                                      | 目前只有 jest-axe 的运行时语义检查，可补静态规则                                                                      |
| P2     | **格式尚未收敛，`format:check` 因此挂在门外** | 全仓保守估计 **360+** 个文件不符合 Prettier（`packages/ui` 245、`packages/x` 单 `src` 85、`icons` 15…）。此前的「假门禁」问题已解决——它的角色已明确为**收敛进度探针**并给了退出判据，同时 `lint-staged` 已在提交期强制格式 | 走增量收敛：只格式暂存文件，随开发逐步归零；**归零后**把 `format:check` 纳入 `verify` 与 CI（判据见「格式策略」一节） |
| P2     | 无依赖更新自动化                              | 无 `.github/dependabot.yml` / `renovate.json`                                                                                                                                                                              | 至少对 devDependencies 开周更                                                                                         |
| P2     | 版本组合偏激进 / 偏旧                         | TypeScript **6**、ESLint **10**、`@typescript-eslint` **8**；同时 pnpm 停在 **7.33.7**（当前已 12.x）                                                                                                                      | 现状可用（lint 全绿），但升级窗口应集中评估一次                                                                       |
| P2     | `skipLibCheck: true` 掩盖声明问题             | 根 `tsconfig.json` 开启；仓库内自查看不到 `.d.ts` 错误                                                                                                                                                                     | 已有 `smoke` 的声明检查部分补偿；验证消费侧类型问题需建临时工程（`skipLibCheck: false`）                              |
| P2     | **门禁链路定义在两处，且无机制保证同步**      | `package.json#verify` 与 `ci.yml` 的各 step 是两份手写清单。本轮修掉的「本地 `verify` 弱于 CI」正是由此而来——改了 `verify` 忘了改 CI（或反之）不会有任何提示                                                               | ① CI 改为单步 `pnpm verify`（换来一致性，牺牲一部分失败可见性）；或 ② 加一个自检脚本比对两处的步骤集合，不一致即失败  |

### 格式策略：已采纳「增量收敛」（2026-09-24 决策）

前提事实：Prettier **没有任何选项能关闭 Markdown 表格对齐**，所以
「保留紧凑表格」与「对 `.md` 跑 prettier」在技术上互斥——必须选一边。

**决策依据是一次实测的规模统计**：仓库中不符合 Prettier 输出的文件规模远超预期——
**仅 `packages/ui` 一个包就有 245 个**，`packages/x` 单 `src` 目录 85 个、
`icons` 15 个、`shared` 5 个、`request` 2 个……全仓保守估计 **360 个以上**
（分片扫描被沙箱中断，实际只会更多）。

这个数字直接否掉了「全量重排」：一个改写 360+ 个文件的 `style:` 提交会让
**整个 `@aura/ui` 的 `git blame` 失去意义**，代价与收益完全不成比例。

| 方式           | 结论                                                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 全量重排     | ❌ **不可行**——360+ 文件，`git blame` 会被淹没                                                                                                                            |
| ② **增量收敛** | ✅ **已采纳**：`.less` / `.md` / `.yml` / `.json` 进入 `lint-staged` 的 `prettier --write`，只格式**暂存**文件、不做全量重排。Prettier 官方对大型代码库也推荐这条迁移路径 |
| ③ 不采纳       | ✗ 未选——放弃格式守护会让样式文件风格持续漂移                                                                                                                              |

**代价（已衡量，接受）**：启用后，**下一次提交会带上该文件的重排噪音**。
按启用时的实测，待提交的 20 个 `.less` / `.md` 文件约产生 **617 行**重排。

**收敛的完成判据（这条必须有，否则会永久悬着）**：

```bash
npx prettier --check "{packages,tests,docs}/**/*.{ts,tsx,js,jsx,json,css,less,md}"
# 输出 "All matched files use Prettier code style!" 时即收敛完成
```

一旦归零，就把 `format:check` 纳入 `pnpm verify` 与 CI，
`format:check` 才算真正成为门禁；在此之前它只是**收敛进度探针**，
不挂在任何关卡上（见「门禁矩阵」）。

## 六、如何扩展

| 场景       | 要做的事                                                                                                                                                                                                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 新增组件   | 按「组件目录约定」建 5 件套；`index.md` 写好 `title` / `group` / `order`，侧栏会自动出现                                                                                                                                                                                                                      |
| 新增包     | 确认 `scripts.build` 含 `father build`（这样 `postbuild-dts` / `smoke` 会自动纳入）；再补三处：`size-limit` 预算、**根 `tsconfig.json` 的 `paths`**、**本包 `tsconfig.json` 的 `paths`**（后者易漏——`ui` / `business` / `x` 都各自声明了一份指向 `../<包名>/src` 的映射，只改根配置在按包构建时仍会解析失败） |
| 新增门禁   | 加进 `package.json` 的 `verify` **和** `.github/workflows/ci.yml` 的对应 step——两处都要动，否则本地与 CI 会分叉                                                                                                                                                                                               |
| 改样式令牌 | 令牌只在 `packages/ui/src/theme/tokens.css` 定义（亮 / 暗两套）；组件 `.less` 只用 `var(--aura-*)`，改完可跑「提取 less 中全部 `var(--aura-*)` × 对比定义」的审计                                                                                                                                             |
